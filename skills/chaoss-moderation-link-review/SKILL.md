# Moderation Link Review

Review an "Add link" submission against the CHAOSS AI Alignment Working Group and integrate the approved link into `moderation/README.md`, the "Awesome LLM Policy" catalog.
The catalog collects published AI-use policies, commentary, tooling, and spam examples from open source projects, companies, foundations, and news outlets.
"Add link" issues are one of the most frequent contribution types in `chaoss/wg-ai-alignment`.
Every submission needs the same decisions: does the link work, is it already listed, which section belongs to it, and how is the entry written.
This skill makes those decisions reproducible so a maintainer resolves an issue in a single pass instead of a comment thread.

## When to use this skill

Use this skill when any of the following is true:

- An issue in `chaoss/wg-ai-alignment` has a title beginning with `Add link:`.
- A maintainer asks to add a link to the moderation catalog.
- A pull request changes `moderation/README.md` and needs review against the catalog conventions.

Scope this skill to `moderation/README.md`.
Working group metrics, meeting notes, and issue-template changes belong to their own workflows.

## Prerequisites

- The `gh` CLI is installed and authenticated against github.com.
  Confirm with `gh auth status`.
- A local clone of `chaoss/wg-ai-alignment` is available, and every command runs from the clone root.
- Write access is not needed to draft a proposal, but the maintainer needs it to commit.

## Reference files

Read each file when the workflow reaches the stage that needs it.

- **[references/section-map.md](references/section-map.md)**: form option to catalog heading map, entry formats for every section, placement and date ordering rules, and the destinations for `Other` submissions.
- **[references/precedents.md](references/precedents.md)**: how past link issues were resolved, commit message conventions, and the failure modes visible in git history.
- **[references/gitmojis.json](references/gitmojis.json)**: the upstream gitmoji list, with `name`, `code`, `emoji`, `description`, and `semver` for every entry. The commit subject uses the `emoji` field of the `memo` entry, written as the character itself.
- **[references/gitmojis-LICENSE.txt](references/gitmojis-LICENSE.txt)**: the MIT license that covers `references/gitmojis.json`. Read it only when redistributing or auditing the vendored data.
- **[assets/issue-comment.md](assets/issue-comment.md)**: closing comment bodies for an added link and for a duplicate.
- **[assets/commit-message.txt](assets/commit-message.txt)**: commit message template with the placeholders this skill fills.

## Workflow

Run the stages in order.
Each stage produces a decision that the next stage depends on.

### Stage 1: Gather the submission

```bash
gh issue view {{ISSUE_NUMBER}} --repo chaoss/wg-ai-alignment \
  --json number,title,author,createdAt,state,body
```

The issue body is generated by the `Add a link` form, so each answer sits under a fixed heading.
Extract these values:

| Field | Issue body heading |
|---|---|
| Link URL | `### Link URL` |
| Link title | `### Link title/name` |
| Requested section | `### Which section does this belong in?` |
| Other description | `### If "Other", please describe` |
| Duplicate attestation | `### Duplicate check` |
| Publication date | `### Date of post/article (if applicable)` |
| Submitter context | `### Additional context (optional)` |

Older issues use `### Additional context` without the parenthetical; treat both spellings as the same field.
The value `_No response_` means the field is empty.

If `Link URL` or `Link title/name` is empty, stop and ask the submitter for the missing value.
Do not infer a URL or a title from the issue title.

Record the extracted values before continuing.
These values fill the header of the proposal in Stage 5.

### Stage 2: Validate the link

Confirm that the URL resolves and that its content matches the claimed category.

```bash
curl -sS -o /dev/null -w '%{http_code} %{url_effective}\n' \
  --max-time 20 -L '{{URL}}'
```

Handle the result with these rules:

- A 2xx status means the link is reachable; continue.
- A 401 or 403 status means the page exists but blocks automated access; report the status and ask the maintainer whether to proceed using their own reading of the page.
- A 404 or 410 status, a DNS failure, or a timeout means the submission is not usable; stop and report the failure with the exact status or error text.
- A redirect to a different host is acceptable when the final URL still serves the submitted resource; record the effective URL.

Read the target page and confirm that it is what the submission claims.
For a policy, the page must describe rules or expectations for AI or LLM use.
For a tool, post, or spam example, the page must match that category.
Report only what the page actually says.
Never describe content that was not fetched, and never recreate a page from memory.

Run the duplicate check against the catalog:

```bash
grep -nF '{{URL}}' moderation/README.md || echo "no exact URL match"
grep -niF '{{PROJECT_NAME}}' moderation/README.md || echo "no project-name match"
```

A match on either command means the link or its project is already listed.
Use a distinctive project name from the issue title, and inspect any line that matches a common word before calling the submission a duplicate.
Report the existing entry and stop the workflow at Stage 5 with the duplicate proposal.

### Stage 3: Choose the section

Open [references/section-map.md](references/section-map.md) and map the form option to a catalog heading.

Treat the submitter's dropdown answer as a claim, not a decision.
The linked content decides the section.
Apply these precedence rules:

1. A policy published by a project repository or project governance body goes to `### Current Project AI Policies`.
2. A policy adopted by a company or foundation goes to `### Organization/Company Policies` or `### Foundation AI Policies`, based on the body that adopted it.
3. An article, interview, or news report goes to `## Blog Posts & News`, even when it reports on a policy.
4. Tooling goes to `## Tools`.
5. An exhibit of bad-faith or low-quality AI contributions goes to `## Spam examples`.
6. A submission marked `Other` follows the `Other destinations` table in the reference.

When two sections are equally defensible, present both in the proposal with one sentence of reasoning and let the maintainer choose.
When the content supports the submitter's choice, keep it and record the confirmation in the proposal.

### Stage 4: Format and place the entry

Use the exact format for the chosen section from [references/section-map.md](references/section-map.md).
The catalog mixes several shapes, and each one signals something different:

```markdown
* [Leptos AI Policy](https://github.com/leptos-rs/leptos/blob/main/AI_POLICY.md)
* Agda ([discussion](https://github.com/agda/agda/pull/8456))
* [Servo](https://book.servo.org/contributing/getting-started.html#ai-contributions) ([discussion](https://github.com/servo/servo/discussions/36379))
* [aittributor](https://github.com/block/aittributor) - AI attribution tooling.
```

The first shape is a standard policy entry.
The second is a policy that exists only as a discussion, pull request, or commit thread.
The third adds a secondary discussion link to a primary policy.
The fourth is a tool entry with a one-sentence description that ends in a period.

For a dated section, derive the year and month from the `Date of post/article` field.
If that field is empty, ask the maintainer which date to use.
Do not substitute the issue creation date without approval.

Placement follows the section rather than the alphabet:

- Policy, tool, and spam entries append after the last bullet in the section list.
- Dated entries go inside the correct `### YEAR` and `#### Month` block.
- A missing year block is created above older years, so 2027 goes above 2026.
- A missing month block is inserted so the year keeps the sort direction it already uses.

Read `references/section-map.md` for the blank-line convention between month blocks.

### Stage 5: Propose the change

Present the proposal to the maintainer in this exact shape:

```text
Issue: #{{ISSUE_NUMBER}} - {{ISSUE_TITLE}}
Author: @{{AUTHOR}}
URL: {{URL}} (HTTP {{HTTP_STATUS}})
Duplicate check: {{DUPLICATE_RESULT}}
Section: {{SECTION_NAME}}
Entry:
{{ENTRY_LINE}}
Placement: {{PLACEMENT}}
```

Write `{{DUPLICATE_RESULT}}` as either `no match for the URL or <project>` or `already listed at line N: <entry>`.
Write `{{PLACEMENT}}` as the heading and the line the entry follows, using line numbers from `grep -n`.

For a discussion-linked policy, say so in the proposal and show the exact line, using the Agda entry from the catalog as the shape:

```text
Section: Current Project AI Policies
Entry:
* Agda ([discussion](https://github.com/agda/agda/pull/8456))
Placement: after the Godot AI policy entry
```

End the proposal with one question: `Apply this entry, or change the section?`

Modify `moderation/README.md` only after the maintainer approves the exact entry.
Approval of a different entry, a different section, or a general instruction to proceed is not approval of this line; show the revised proposal and ask again.

### Stage 6: Apply the change and prepare the commit

Insert the approved line at the agreed position and change nothing else.
Write the new line in plain ASCII with straight quotes, and keep the existing bullet character.

```bash
git diff -- moderation/README.md
```

Confirm that the diff contains exactly one added line.
If the diff contains a deleted line, a moved entry, a re-indented entry, or a whitespace change, undo your edit and ask the maintainer before retrying.
Never run `git restore` on a file that already had uncommitted changes when the workflow started.

Apply the 50/72 rule when filling the template:

- Start the subject with the character from the `emoji` field of the `memo` entry in [references/gitmojis.json](references/gitmojis.json). Write the emoji character itself; git does not expand a `:memo:` shortcode.
- Keep the subject line within 50 characters, including the emoji and the `moderation:` component.
- Keep every body line within 72 characters and fill each line greedily, so a line breaks only when the next word would cross the limit.
- Separate the subject, the body, and the trailer block with single blank lines.
- Backtick file names, paths, commands, flags, and identifiers, and keep each backticked span on one line.
  Move the complete span to the next line when it would cross the 72-character limit.

Fill [assets/commit-message.txt](assets/commit-message.txt), write the result to `/tmp/opencode/wg-ai-alignment-add-link-{{ISSUE_NUMBER}}.txt`, and present the command:

```bash
git add moderation/README.md
git commit --edit --file=/tmp/opencode/wg-ai-alignment-add-link-{{ISSUE_NUMBER}}.txt --signoff
git push origin main
```

Add `--gpg-sign` after the `--file` argument when the maintainer signs commits.
Hand the command to the maintainer and wait for confirmation that the push completed.

When the maintainer prefers review instead of a direct push, use a branch and a pull request:

```bash
git switch -c add-link-{{SLUG}}
git add moderation/README.md
git commit --edit --file=/tmp/opencode/wg-ai-alignment-add-link-{{ISSUE_NUMBER}}.txt --signoff
git push -u origin add-link-{{SLUG}}
gh pr create --repo chaoss/wg-ai-alignment --title "Add {{ENTRY_NAME}}" --body "Closes #{{ISSUE_NUMBER}}"
```

Show the pull request command and its body before it runs, because `gh pr create` publishes content under the maintainer's account.

### Stage 7: Close the loop

Close the issue only after the commit is on `main` or the pull request is merged.
Confirm the commit first:

```bash
git log -1 --format='%h %s' -- moderation/README.md
```

Fill the matching block in [assets/issue-comment.md](assets/issue-comment.md), write it to `/tmp/opencode/wg-ai-alignment-issue-{{ISSUE_NUMBER}}-comment.md`, and present the rendered comment to the maintainer.
Post the comment and close the issue only after the maintainer approves that exact text and authorizes the two commands:

```bash
gh issue comment {{ISSUE_NUMBER}} --repo chaoss/wg-ai-alignment \
  --body-file /tmp/opencode/wg-ai-alignment-issue-{{ISSUE_NUMBER}}-comment.md
gh issue close {{ISSUE_NUMBER}} --repo chaoss/wg-ai-alignment --reason completed
```

Use `--reason "not planned"` when closing a duplicate or an unusable submission.

Verify the result read-only:

```bash
gh issue view {{ISSUE_NUMBER}} --repo chaoss/wg-ai-alignment \
  --json state,stateReason,comments \
  --jq '{state: .state, stateReason: .stateReason, comments: [.comments[].body]}'
```

Confirm the state is `CLOSED`, the reason is `COMPLETED` for an added link or `NOT_PLANNED` for a duplicate, and exactly one new comment exists.

## Failure handling

| Situation | Action |
|---|---|
| URL returns 404, 410, or does not resolve | Stop and report the status code or error. Ask the submitter for a working URL. |
| URL is reachable but blocks automated access | Report the status, ask the maintainer to read the page, and use their summary. |
| Link or project already in the catalog | Present the existing entry and propose a duplicate close with `--reason "not planned"`. |
| Section is ambiguous | Present both candidates with reasoning and let the maintainer choose. |
| Policy spans several files or lives in a pull request | Link the discussion thread in the `* Name ([discussion](https://github.com/agda/agda/pull/8456))` form. |
| Submission asks for a new section | Add the link to `## Other Resources` and tell the maintainer a new heading needs a separate change. |
| Issue form gained a new field | Read `.github/ISSUE_TEMPLATE/add-link.yml` and map the new field before continuing. |

## Placeholders

| Placeholder | Description | Source |
|---|---|---|
| `{{ISSUE_NUMBER}}` | Number of the "Add link" issue | Stage 1 |
| `{{ISSUE_TITLE}}` | Issue title, including the `Add link:` prefix | Stage 1 |
| `{{URL}}` | Submitted link, preserved exactly as written | Stage 1 |
| `{{PROJECT_NAME}}` | Project or organization name used for the duplicate search | Issue title or page content |
| `{{HTTP_STATUS}}` | Final HTTP status code from the validation request | Stage 2 |
| `{{DUPLICATE_RESULT}}` | Duplicate search outcome in the prescribed wording | Stage 2 |
| `{{SECTION_NAME}}` | Catalog heading chosen for the entry | Stage 3 |
| `{{ENTRY_LINE}}` | Complete catalog line, including the leading `* ` | Stage 4 |
| `{{PLACEMENT}}` | Heading and preceding line for the insertion point | Stage 4 |
| `{{ENTRY_NAME}}` | Short name used in the commit subject and pull request title; keep the full subject within 50 characters | Stage 4 |
| `{{RATIONALE}}` | One to three sentences explaining why the link belongs | Stage 6 |
| `{{SLUG}}` | Lowercase hyphenated branch suffix, such as `tock-policy` | Stage 6 |
| `{{AUTHOR}}` | GitHub handle of the issue submitter | Stage 1 |
| `{{COMMIT_SHA}}` | Short hash of the commit that added the link | Stage 7 |
| `{{EXISTING_ENTRY}}` | Existing catalog line when a link is already present | Stage 2 |
| `{{MAINTAINER_HANDLE}}` | GitHub handle of the maintainer posting the comment | Stage 7 |

## Boundaries

- Read the catalog before editing it, and base every claim on a fetched page or a local file line.
- Draft local edits only after the maintainer approves the exact entry line, and keep each edit to one added line.
- Print commands for commits, pushes, comments, closes, and pull requests, then let the maintainer run them.
  When the maintainer delegates execution, require explicit approval of that exact payload in the conversation.
- Attribute quoted submitter text with its issue number instead of paraphrasing it into the catalog.
- Leave unrelated entries untouched, including typos and inconsistent formatting, and mention them to the maintainer as a follow-up.

## Quality checklist

Run this checklist before presenting the Stage 5 proposal:

- [ ] URL fetched with a recorded status code.
- [ ] Page content read and matched to the claimed category.
- [ ] Duplicate search run for the URL and the project name.
- [ ] Section confirmed against `references/section-map.md`.
- [ ] Entry line matches the section format exactly.
- [ ] Placement preserves the existing sort direction.
- [ ] Commit subject within 50 characters and body lines within 72 characters.
- [ ] Commit subject starts with the actual emoji character, not a `:shortcode:`.
- [ ] Public text is plain ASCII with straight quotes.
- [ ] Every placeholder in the proposal is filled.
